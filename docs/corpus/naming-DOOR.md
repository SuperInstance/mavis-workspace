## 0. Three findings that change the brief

I was handed three things as settled. Two did not survive checking, and one grew.

### 0.1 `RenderContext::from_repo` reads nothing. The renderer is a stub.

The brief says "`RenderContext::from_repo` reads a repository." It does not.
`lau-git-render/src/lib.rs:127-129`:

```rust
pub fn from_repo(_repo_path: &str) -> Result<Self, RenderError> {
    // In a real implementation, this would read git refs, parse state files, etc.
    // For now returns a stub that demonstrates the shape.
```

The next 23 lines return `String::new()`, `0`, and empty `Vec`s. The parameter is
underscore-prefixed — the compiler is telling us it is unused. `RenderContext::from_repo`
(line 166) wraps it faithfully, so the whole call chain terminates in a hardcoded empty
snapshot. **`lau-git-render` cannot render a repository, because it never looks at one.**

The crate is not nothing — 2,477 lines, 8 renderers, 96 tests, CI, MIT, and a real
`Renderer` trait. But its reason for existing, reading a repo, is unwritten, and
`git log` shows the last push was **2026-07-12, 82 days ago**, while the account pushed
this morning.

### 0.2 The front door already exists. It is called `quilt-atlas`.

The brief says the dormant renderer "already knows how to fix" the front door. A better
tool already has the job, and is not dormant:

> `SuperInstance/quilt-atlas` — "The living map of the SuperInstance account: 4000+
> repos, families, motion, CI coverage. Regenerated by its own scheduled workflow every 6h."

JavaScript, 723 KB, **pushed 2026-10-02T15:55Z — one hour before this session started.**
`scripts/build_atlas.mjs` (214 lines) follows `Link: rel="next"` to exhaustion and emits
`atlas.json` classifying **all 5,138 repos** with per-repo evidence
(`[family, stage, matched keywords, language]`). It carries its own honesty laws —
"absence elsewhere is **UNMEASURED**, never reported as zero."

So the question is not *which tool becomes the front door*. It is *why a live, correct,
self-regenerating map is invisible from the profile page.* That is a linking problem,
and it is fixed by two sentences, not a rename.

### 0.3 The GitHub API returned a false 404 for a repo that exists.

`GET /repos/SuperInstance/SuperInstance` returned **404**. The same URL returned **200**
sixty seconds later, and on 12/12 consecutive probes thereafter. The repo is public, has
a 25,827-byte README on its default branch, and renders on the profile page.

Observed rate: **1 false 404 in 13 probes.** I am not claiming a rate I cannot support
from one event — I am reporting that it happened once, to me, today, on the exact call
this task depends on.

**This is the mechanism behind the orchestrator's two clobbered repos.** A single 404
read as "free" is a rename onto a name someone already holds. The collision protocol
this document uses is therefore:

> **A name is FREE only if the HTML route *and* the API route both return 404, on two
> separate probes.** One 404 is not evidence. One 200 is disqualifying.

HTML probes cost no API quota, so the cheap route is the primary one. Every name below
was checked on both.

### 1c. Why this wording, and the one sentence that matters

**The destination sentence is the highest-value text in the file.** A scout handed a
verified defect and no destination does not stay silent — it opens issue #5,142. The
routing rule ("repo issue with a reproducible counter-example → `fleet-triage` for the
unattributable → *don't file if unsure*") is what makes the account's confident-wrong-claim
failure mode visible *before* a reader trusts a theorem, instead of after they cite it.

The third limb — **not sure, don't file** — is the one most index pages omit, and it is
the one that protects the account from its own failure mode. Half the value here is
refusing to publish an unverified claim.

The block also leads with `quilt-atlas` rather than `quilt`, which inverts the brief's
ordering: the flagship is the substrate, but the *front door* is the map. A reader with a
task wants the index first and the philosophy second.

**Length:** 30 lines, ~2,900 characters. At a screen, it costs one scroll of the existing
25,827-byte page. It is deletable without touching a word below it.

### 2.2 `lau-git-render` — **do not rename it yet. Finish it first.**

I am declining the rename the brief asked for, on evidence, and I want the decline to be
legible rather than a dodge.

A front door is load-bearing: it is the first thing a stranger trusts. `lau-git-render`
cannot currently read a repository (§0.1). Renaming it to a public-face name would make
a stub load-bearing — it would promise a map and serve a blank. The brief's premise, that
this is the tool that "already knows how to fix" the door, is false in the one place that
matters.

**The rename is the last step, not the first.** Write `from_repo`, then name it.

If you want the name decided now anyway, two free options, neither of which I recommend
publishing yet:

- **`ensign-render`** — the name the repo's own `AGENT.md` already uses in its title line
  ("# Ensign Render — lau-git-render"), and it fits the account's nautical agent
  convention (`AGENT.md` names neighbours "Temporal Heartbeat Keeper", "A2A Transport
  Operator", "Grammar Conductor"). Convention-preserving, but opaque to anyone outside
  the account — which is disqualifying for a *front door*.
- **`quilt-render`** — findable in the `quilt-*` namespace, which is the account's real
  index, but it is the vaguest of the three and says nothing about the job.

Neither is worth publishing while line 127 returns an empty struct. **If `quilt-atlas`
stays the front door — and §0.2 says it should — this rename may never be needed.**

### 2.3 `quilt-adjudication` → **`git-adjudication`** (free, both routes, 404/404)

The brief's premise here holds. The repo is **Shell**, 119 KB, and it is a git merge
protocol. It is misfiled under a namespace that means "cell/sheet runtime," which sends
a reader looking for a grid library and away from the account's best argument.

Recommended diff, nothing applied:

```

```

Rationale: keeps the token a scout actually searches (`adjudicate`/`adjudication`),
states the substrate it operates on, and stops claiming a quilt it is not built from.

**Cost, stated plainly:** renaming is a breaking change to every link anyone has ever
made, to the repo's own README, and to its `Cargo`/entry references. It is 0★ with a
2026-10-02 push, so the blast radius is likely small — but that is an inference, not a
measurement, and it is your call, not mine.

**One correction to the brief's §3.** `quilt-adjudication` is *not* undescribed. Its
current description reads:

> merge that records its disputes instead of discarding them. No judge in the loop, by design."

It already ranks #1 for `merge` and `judge`. Its findability problem is the **name**,
not the description — which is why the rename above is the real fix and a description
rewrite would be busywork. I have not rewritten it.

## 4. A correction to the structural finding in `AGENT-ENTRY.md`

`fleet-triage/AGENT-ENTRY.md` §6 states:

> "The repos API does not index this account. The work is reachable by name and by search
> term, and unreachable by any list."

**This is refuted, and it is refuted by the account's own tooling.**
`quilt-atlas/scripts/build_atlas.mjs` walks `Link: rel="next"` to exhaustion and holds
**5,138 repos** in `atlas.json` (`pagination_cap_hit: false`, 52 pages). I checked the
specific repo the earlier log said was missing:

```
constraint-theory-core  ->  ['other', 'none', '', 'Rust']   # PRESENT
```

The earlier scout paged 4,000 entries by hand and did not reach it; `quilt-atlas` reached
all 5,138 by following one header. The listing works. What fails is paging it
manually and assuming you have seen everything.

**Why this changes the remedy.** The earlier log concluded this was *"not primarily a
description problem — it is an index problem."* But `atlas.json` shows the listing
carries `description` for every repo (the atlas classifier scores on it), and the live
count is 5,140. **Adding a description puts a repo in front of a name-based classifier
and a human's search, on a route that demonstrably works.** Description-filling is a
working lever, not a weak one — which makes §3 worth doing, and makes the front-door
block in §1b cheap rather than heroic.
